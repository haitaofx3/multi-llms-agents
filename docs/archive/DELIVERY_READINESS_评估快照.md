# 可交付性评估与后续优化方向

> 视角：把本项目当作**要交付给他人使用的产品**（而非个人实验）来看，还差什么。
> 基线：P0 / P1 / P2 改造完成后（157 项用例全绿、ruff 与 mypy 双门禁通过、编排器完成分层拆包）。
> 结论先行：**单机单人场景已达"可交付"水平；多用户 / 对外服务 / 长期运维三个方向仍有明确缺口。**

## 二、上线必需（缺了就不该对外提供服务）

| # | 缺口 | 现状 | 建议动作 | 工作量 |
| --- | --- | --- | --- | --- |
| A1 | **速率限制** | 无。一个脚本可反复 `/api/configure` + `/api/start` 刷爆额度 | 反向代理层（Nginx `limit_req`）或中间件令牌桶，按 IP + session 双维度 | S |
| A2 | **健康检查与就绪探针** | 无 `/healthz`；编排器可用性无信号 | 增加 `/healthz`（进程存活）与 `/readyz`（向量库后端、嵌入后端、线程池状态） | S |
| A3 | **审计日志** | 结构化日志只进 stdout，不落盘、无保留策略 | `logging` 增加轮转文件 handler（或接入 Loki/ELK）；关键操作（configure/start/end/鉴权失败）单独审计事件 | S–M |
| A4 | **HTTPS 终结** | 裸 uvicorn | 部署文档明确 Nginx/Caddy 反代 + `wss`；`start.py` 保持只绑本机 | S |
| A5 | **依赖锁定** | `requirements.txt` 全 `>=`，构建不可复现 | `pip-compile` / `uv lock` 出 `requirements.lock`；CI 用锁文件安装 | S |
| A6 | **崩溃可恢复** | 讨论中进程退出 → 只有元数据快照，发言内容丢失（重启后标 `interrupted`） | 每轮结束把 transcript 增量追加写入 `data/discussions/{trace}.jsonl`；重启可回放/续跑 | M |

## 五、产品化缺口（决定"好不好用"）

| # | 缺口 | 说明 |
| --- | --- | --- |
| D1 | 无多用户与权限 | 会话靠浏览器 `localStorage` 的随机 id 隔离，本质是"匿名会话"；无账号体系、无会话归属校验（知道 sid 即可操作） |
| D2 | 历史讨论无管理 | 只有列表 + 查看 + 下载；缺删除、批量清理、标签、按主题聚合 |
| D3 | 知识库无后台 | 上传即注入全局共享库，无法查看/删除已注入内容，也无法按会话隔离知识 |
| D4 | 费用无预算护栏 | 只有只读遥测与事后估算；缺"单场预算上限 → 提前收敛"的可选开关（当前是刻意移除预算约束的设计） |
| D5 | 模型目录需手填 | 自定义 provider 要手填 base_url/model_id；可加常用供应商与模型名下拉 + 连通性自检按钮 |
| D6 | 无"继续讨论" | 讨论结束后无法带着上下文追加追问（`run_discussion` 会重置运行态） |

## 六、架构演进（按需，不要过早做）

来自 `P2优化方案.md` 的方向仍然成立，前提是出现对应需求：

- **多实例部署**：事件总线换 Redis Streams / MQ，共享黑板换 Redis Hash，会话注册表分布式化 —— 只有"多人同时用或需要横向扩容"时才值得。
- **人工审核（human-in-loop）**：每轮暂停等人工放行 + `POST /api/intervene` 注入指令 —— 教学/内容审核场景价值高。
- **观测栈**：OpenTelemetry trace + Prometheus 指标 + Grafana 面板 —— 一旦对外服务就该有。
- **讨论快照与回放**：每轮黑板状态 JSON 快照，支持按快照复现问题。

## 七、明确**不建议**做的（避免过度设计）

1. **不要把 token 预算系统加回来**：`FairnessGovernor` 用"字符 + 相对比例"是经过论证的正确选择（跨模型 token 不可比）；预算护栏若要做，应作为"费用上限 → 提前收敛"的**独立可选开关**，不要混入公平性治理。
2. **不要为了"看起来专业"引入 Redis/PG**：当前单进程 + 文件持久化在单机场景足够；引入外部中间件前先证明有并发/多实例需求。
3. **不要全面改写编排器**：拆包已完成，剩余耦合（prompt 与状态交织）性价比低；继续拆的收益小于风险。
4. **不要给前端加构建链**：零构建是当前部署优势（改完刷新即生效），除非要做多页面/多人协作。

## 八、建议的落地顺序（按投入产出比）

1. **一周内可完成**：依赖锁定（A5）、`/healthz` `/readyz`（A2）、日志落盘（A3）、CI 覆盖率门禁（B5）、质量基线入库（C2）。
2. **两周内**：速率限制（A1）+ 部署文档（A4）、错误契约统一（B3）、容器化（B1）、讨论增量落盘（A6）。
3. **按需求触发**：多用户与权限（D1）、知识库后台（D3）、人工审核、多实例基础设施。
